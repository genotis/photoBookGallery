# 04. 압축파일 처리 전략 (핵심 문서)

본 프로젝트의 가장 까다로운 부분. **읽기(비파괴)** 와 **쓰기(삭제+재압축)** 를
분리해서 다룬다.

## 1. 포맷 정리

| 확장자 | 실제 포맷 | 읽기 | 쓰기(생성/수정) |
|--------|-----------|------|-----------------|
| `.zip` | ZIP | ✅ 오픈소스 | ✅ 오픈소스 |
| `.cbz` | ZIP (만화책 관례) | ✅ | ✅ |
| `.rar` | RAR | ✅ (unrar, 읽기 전용) | ❌ 오픈소스 불가 |
| `.cbr` | RAR (만화책 관례) | ✅ | ❌ |
| `.7z`  | 7-Zip | ✅ (확장) | ✅ (확장, 7z 바이너리) |

> 핵심 사실: **CBR = RAR 컨테이너.** RAR 포맷의 **생성/수정은 독점 소프트웨어
> (WinRAR의 `rar`)만 가능**하다. `unrar`는 공개되어 있으나 **읽기 전용**이며,
> 라이선스상 "unrar 소스를 RAR 호환 압축기 제작에 사용하는 것"을 금지한다.
> 따라서 오픈소스/배포 가능한 스택만으로는 RAR을 **수정할 수 없다.**

## 2. 읽기 전략 (비파괴, 모든 포맷)

목표: **압축 해제 없이** 엔트리 목록과 개별 이미지를 온디맨드로 얻는다.

### 2.1 ZIP/CBZ
- `node-stream-zip`로 중앙 디렉터리만 읽어 엔트리 목록 즉시 확보.
- 특정 엔트리만 스트림으로 추출 → sharp로 썸네일/리사이즈 → 캐시.

### 2.2 RAR/CBR
- `node-unrar-js`(WASM)로 헤더 파싱 → 엔트리 목록.
- 개별 엔트리 추출 가능. **단, solid 압축(solid archive)** 의 경우 임의 엔트리
  접근 시 앞쪽 데이터까지 풀어야 해 비용이 큼 → 표지/썸네일 우선, 본 뷰는
  추출 결과를 단기 캐시.
- WASM 성능이 부족하거나 대용량 RAR이 많으면 보조 경로로 컨테이너 내
  `unrar` 바이너리를 `child_process`로 호출(스트리밍 추출).

### 2.3 공통
- **엔트리 필터링**: 이미지 확장자(jpg/jpeg/png/webp/gif/avif)만 페이지로 인식.
- **자연 정렬**: 파일명 숫자 구간을 수치 비교(`page2 < page10`).
- **표지 결정**: 정렬 후 첫 이미지, 또는 사용자가 지정한 대표 페이지.

## 3. 쓰기 전략 (개별 파일 삭제 후 재압축)

### 3.1 ZIP/CBZ 원본 → 그대로 ZIP 재생성
1. 원본 ZIP 엔트리 순회.
2. 삭제 대상 엔트리를 **제외**하고 새 ZIP에 복사(`yazl`/`archiver`).
3. 임시 파일로 생성 → 무결성 검증 → 원자적 교체.

### 3.2 RAR/CBR 원본 → **CBZ(ZIP)로 변환 저장** (오픈소스 경로)
RAR을 다시 RAR로 쓸 수 없으므로:
1. `unrar`(WASM 또는 바이너리)로 필요한 엔트리들을 추출(삭제 대상 제외).
2. 추출 이미지들을 새 **ZIP(.cbz)** 로 패키징.
3. 결과 정책에 따라 저장(아래 4절).
- 결과적으로 라이브러리에서 RAR 비중이 점차 ZIP으로 정규화됨(편집된 것부터).

### 3.3 (선택) 7z 바이너리 경유 통합 경로
- 컨테이너에 `p7zip`(`7z`) 포함 시, 7z로 RAR 읽기 + ZIP/7z 쓰기를 한 도구로 처리 가능.
- 단 RAR **쓰기**는 7z로도 불가(읽기만). 결국 출력은 ZIP/7z.
- 의존성 단순화를 위해 **단계 1은 Node 라이브러리(zip 쓰기 + unrar 읽기)** 로
  구현하고, 7z 바이너리는 성능/포맷 확장이 필요할 때 도입.

## 4. 편집 결과 저장 정책 (확정: 원본 백업 후 ZIP 교체)

**원본을 백업 경로로 보관한 뒤, 활성 위치를 새 ZIP(.cbz)으로 교체한다.**
ZIP 원본도, CBR/RAR 원본도 동일한 절차를 따른다(결과는 항상 `.cbz`).

### 절차
```
1. 임시 경로에 새 ZIP 생성 (삭제 대상 엔트리 제외)
2. 무결성 검증: 엔트리 수 일치 + 표본 이미지 디코드 성공
3. 원본을 백업 경로로 이동/복사:
     <backupRoot>/<원본 상대경로>.<timestamp>.<원본확장자>
   (예: /app/backups/photobooks/foo/bar.cbr.20260529-1200.cbr)
4. 활성 위치에 새 .cbz 배치:
     - ZIP 원본: 같은 이름으로 교체(원본은 백업에 보존)
     - CBR/RAR 원본: 확장자가 .cbz로 변경됨(원본 .cbr은 백업에 보존)
5. DB 레코드 갱신: 새 contentHash로 update(메타데이터 승계),
   path/format/pageCount 갱신, 관련 썸네일/엔트리 캐시 무효화
```

### 백업 경로
- 별도 볼륨/디렉터리(`<backupRoot>`)에 보관. 미디어 루트와 분리 권장.
- 백업은 자동 삭제하지 않음(수동 정리 또는 보존 기간 정책은 추후).
- 백업본 위치는 감사 로그에 기록(원본↔결과 매핑, 삭제한 엔트리 목록, 해시).

### 원자성 / 안전
- 모든 쓰기는 **임시 파일 → 검증 → (원본 백업) → 활성 위치 교체(atomic rename)**.
- 검증 실패 시 임시 파일 폐기, 원본/활성 위치 미변경, 작업 실패 보고.
- 동일 아카이브 동시 편집은 파일 단위 락으로 직렬화.

## 5. 안전장치
- **파일 단위 락**: 동일 아카이브 동시 편집 직렬화.
- **경로 검증**: 미디어 루트 화이트리스트 + 정규화로 traversal 차단.
- **무결성 검증 실패 시** 원본 미변경, 임시 파일 폐기, 작업 실패 보고.
- **권한**: 편집 대상 경로는 컨테이너에 RW로 마운트. 단순 브라우징만 할 경로는
  RO로 분리 가능.
- **로그/감사**: 어떤 엔트리를 삭제했는지, 원본/결과 경로, 해시 기록.

## 6. 요약 결정
- 읽기: ZIP/CBZ/RAR/CBR 모두 **압축 해제 없이** 지원.
- 쓰기: **ZIP만 네이티브 지원.** CBR/RAR 편집은 **CBZ로 재패키징**한다.
- 저장 정책(확정): **원본을 백업 경로로 보관 후, 활성 위치를 새 ZIP으로 교체.**
